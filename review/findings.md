## U-01 エラーダイアログの Discard が機能せず、文言も誤解を招く

**重大度**: Medium / **区分**: エラー回復

**対応状況（フェーズ1・実装済み）** — エラー表示を閉じられるバナーと詳細欄に変更し、破棄確認を文書の入れ替え操作に移した。

**確認結果** — 保存失敗のバナーを閉じても未保存編集が残ることを統合テストで確認。Windows 実機でも、ネイティブ保存失敗後に「エラーを閉じる」を押すと、破棄確認を開かずにバナーが消え、追記と未保存表示が残った。[Windows 実機の検証記録](improvement-plan.md#windows-のフェーズ1追加検証2026-11-08)

**根拠**
- `src/App.tsx:200` で `pendingRef` を宣言しているが、値を代入している箇所がリポジトリ内に存在しない（読み取りは `App.tsx:1247` のみ）。
- `src/App.tsx:1245-1251` の `resolveDiscard` は `pendingRef.current` が null のため、`discard === true` でも何も実行しない。
- `src/App.tsx:1595-1605` で `doc?.dirty` のとき **Discard** と **Cancel** を表示する。

**ユーザーへの影響**
未保存状態でエラーが起きると「Discard」が出るため、ユーザーは「破棄して続行できる」と期待する。しかし押しても何も起きず、ダイアログが閉じるだけ。編集内容は保持される。実際の破棄確認は別の操作で行われるため、ここで表示されるボタンはユーザーに誤った選択肢を示している。

**改善案**
- エラー表示は閉じる操作に一本化する。未保存変更の破棄確認は `confirmReplaceDirtyDocument` に集約し、実行する操作を確認文に含める。

## U-02 確認・入力にブラウザ標準ダイアログを使い、言語・文脈が不足

**重大度**: Medium / **区分**: 一貫性・入力体験

**対応状況（フェーズ4・実装済み）** — 破棄・削除・リネーム・移動・追加の確認と入力をアプリ内ダイアログに統一した。リネームは拡張子を固定し、移動先はフォルダの選択欄で指定する。

**確認結果** — 統合テストで入力検証、移動、削除の確定・取消を確認。Windows 版では文書切り替え時の破棄確認を確認。

**ツリー操作の追補（2026-11-08）** — 移動先を階層で選べるようにし、ツリーの右クリックメニューから Markdown とフォルダをインラインで追加できるようにした。Windows 版で、移動の取消・確定、本文リンクの更新、追加時の入力検証と保存を確認した。[実機検証](improvement-plan.md#windows-の移動先ツリーとインライン追加の検証2026-11-08) · [PR #40](https://github.com/mdpkg/MaCaEditor/pull/40)

**根拠**
- `App.tsx:288` `window.confirm("Discard unsaved changes?")`
- `App.tsx:1141` `window.confirm(\`Delete ${fileName}? ${references} Markdown reference...\`)`
- `App.tsx:467` `window.prompt("New folder name", "untitled")`
- `App.tsx:1066` `window.prompt("New name", fileName)`
- `App.tsx:1102` `window.prompt("Destination path", path)`
- `App.tsx:1119` `window.prompt("Markdown path", ...)`
- `App.tsx:1131` `window.prompt("Folder path (empty folders are not saved)", ...)`

**ユーザーへの影響**
- アプリ内 UI はボタンやメニューで構成されているのに、確認だけ WebView の標準ダイアログが出る。見た目・操作感の一貫性が崩れる。
- 文言が英語のみで、日本語 UI を期待したユーザーには読みにくい（U-09 と関連）。
- `window.prompt` は入力途中の検証ができず、不正なパスを入れてから初めてエラーになる。
- リネームでは「New name」とだけ聞かれ、拡張子を消すと種別が変わる危険がある（例: `index.md` → `index`）。
- 移動では「Destination path」とパッケージ内の相対パスの手入力を要求され、階層構造を頭の中で組み立てる必要がある。

**改善案**
- 破棄確認・削除確認はアプリ内モーダルに統一し、対象名と影響（参照数）を明示する。
- リネームはファイル名のみを編集させ、拡張子は固定表示にする。
- 移動はフォルダツリーから移動先を選ぶピッカーにする（D&D があるので、右クリックの Move も同じ操作系に寄せる）。
- 新規 Markdown / フォルダ追加は、現在のフォルダを初期値にしたインライン入力にする。

## U-03 外部変更の競合時に再読込の導線がない

**重大度**: High / **区分**: エラー回復

**対応状況（フェーズ1・実装済み）** — 競合中の通常保存を止め、バナーに理由、パッケージ書き出し、破棄確認付きの再読込を表示する。

**確認結果** — 統合テストに加え、2026-11-07 に Windows Tauri 版（`1f485cb`、WebView2）で確認した。未保存の編集がある状態で別プロセスの Git for Windows 付属 Vim が元ファイルを保存し、実際のフォルダ監視で競合が検知された。メニューと `Ctrl+S` から通常保存は実行されず、外部版はディスクに残った。退避した `.mdpkg` を実際に読み戻し、未保存の追記を確認した。再読込を取り消すと追記・未保存状態・競合バナーが維持され、破棄を確定すると外部版が表示されて競合が解消した。その後の通常保存で外部版への追記を書き込めた。

**検証条件** — 一時フォルダを使用し、退避先の選択ダイアログは一時パッケージを返すようにした。競合イベント、ファイル監視、書き出し、再読込には実際の Tauri 処理を使用した。

**根拠**
- `App.tsx` の Folder 監視 effect で、競合時に `externalConflictRef.current = true` とし、`showNotification("外部変更を検知しました。未保存の編集があるため自動反映していません", "error")` を出す。
- `performSave` は `externalConflictRef.current` が true のとき `setError("External changes conflict with unsaved edits. Reopen the folder before saving.")` で保存を中止する。
- 競合通知に再読込・退避の操作はない。Folder モードの **File → Export Package...** は通常保存とは別の処理で、編集中の内容を `.mdpkg` に書き出せる（`App.tsx:625`、`Toolbar.tsx:154`）。

**ユーザーへの影響**
競合時は通常保存が止まる。ユーザーは自分でフォルダを選び直して変更の破棄を確認するか、File メニューで退避手段を見つける必要がある。

**改善案**
- 競合バナーに「再読込（ローカル編集を破棄）」「パッケージに書き出す」のボタンを置く。
- 少なくとも「再読込」ボタンは必須。押下時に未保存破棄の確認を挟む。
- 競合中は Save ボタンを無効化し、理由をツールチップで示す（現在は押せてしまい、押すとエラーになる）。

## U-04 通知バナーが 3.5 秒で自動消滅し、手動で閉じられない

**重大度**: Medium / **区分**: フィードバック

**対応状況（フェーズ1・実装済み）** — エラー通知を閉じるまで保持し、時間制限のある通知はホバー中に残り時間を停止する。フェーズ5でフォーカス中の停止も追加した。

**確認結果** — 仮想タイマーを使ったテストで手動終了、ホバーによる停止と残り時間経過後の消去を確認。Windows 実機ではフォルダの外部更新による情報通知が約3.5秒で消え、ホバー中とフォーカス中はそれぞれ約4.2秒維持できた。解除後は残り約2.7秒で消えた。情報通知と再読込エラー通知の手動終了、エラー通知の保持も確認した。[Windows 実機の検証記録](improvement-plan.md#windows-のフェーズ1追加検証2026-11-08)

**通知履歴の実機確認（2026-11-08）** — ステータスバーから起動中の直近50件を新しい順に振り返れる。Windows 版で、自動消去された情報通知と手動で閉じたエラー通知を確認した。エラー原文は「詳細」で開けた。[実機検証](improvement-plan.md#windows-での通知履歴の検証2026-11-08) · [PR #37](https://github.com/mdpkg/MaCaEditor/pull/37)

**根拠**
- `App.tsx` の `showNotification` で `window.setTimeout(..., 3500)` により自動削除。
- `src/components/NotificationBanners.tsx` はメッセージを表示するだけで、閉じるボタンもホバー停止もない。

**ユーザーへの影響**
- エラー（例: ダウンロード失敗、フォルダ監視開始失敗）が 3.5 秒で消えるため、読み切れない・見逃す。
- 長いファイル名やパスを含むメッセージは特に読み切れない。
- 消えた通知を後から確認する履歴もない。この制限は通知バナーに適用され、別に表示されるエラーダイアログは手動で閉じられる。

**改善案**
- error トーンは自動消滅させない、または 10 秒以上にする。
- 各バナーに閉じるボタンを付ける。
- ホバー中はタイマーを止める。
- 直近の通知をステータスバーやログから確認できるようにする。

## U-05 ツリーをキーボードで操作できず、メニューとダイアログにも操作上の不足がある

**重大度**: High / **区分**: アクセシビリティ

**対応状況（フェーズ2・実装済み）** — ツリーに矢印キーと Enter、メニューに矢印キー・Home/End・Esc、共通ダイアログに初期フォーカス・トラップ・復元を実装した。検索と診断はフェーズ5で本文を操作できる非モーダルのパネルに変更した。

**確認結果** — 2026-11-07 に Windows Tauri 版（`1f485cb`、WebView2）で通し操作を確認した。Tab からファイルメニューを開き、矢印キー・Home・End で移動し、Esc でメニューボタンに戻った。ヘルプのショートカット一覧を Enter で開いて Esc で閉じた。ツリーで `docs` を閉じて開き直し、`guide.md` を Enter で開いて Tab と Enter で編集へ進んだ。WebView2 のアクセシビリティツリーには「パッケージ内のファイル」、フォルダの展開状態、`guide.md` のレベル2・選択・フォーカスが出た。

**ナレーター追加確認（2026-11-07）** — Windows ナレーターの「スピーチの要約」に、ツリー名「パッケージ内のファイル」、`guide.md` の「レベル 2」「選択されています」が記録された。親フォルダ `docs` では「レベル 1」「展開されています」を、開閉ボタンで折りたたむと「たたまれています」を確認した。

**根拠**
- `src/components/FileTree.tsx` のファイル項目は `<div onClick>` で、`tabIndex` / `role` / `onKeyDown` がない。フォーカスも当たらない。
- フォルダ項目も `<div onClick={() => setOpen(...)}>` で、キーボードで開閉できない。
- `src/components/Toolbar.tsx` のメニューは `role="menu"` / `role="menuitem"` を持つが、矢印キー移動・Esc で閉じる処理がない（外側クリックのみ）。
- `AboutDialog` 以外のダイアログ（`ManifestEditorDialog`, `InferredManifestDialog`, `V1MigrationDialog`, `BacklinksDialog`, `PackageSearchDialog`, `PackageDiagnosticsDialog`）は Esc 処理を持たない。`PackageSearchDialog` は検索欄に `autoFocus` があり、列挙した他のダイアログには明示的な初期フォーカスがない。

**ユーザーへの影響**
ツリーからファイルを開く操作やフォルダの開閉にマウスが必要。メニュー項目やダイアログのボタンは Tab と Enter で操作できるが、矢印移動、Esc、フォーカス管理に不足がある。

**改善案**
- ツリー項目を `<button>` または `role="treeitem"` + `tabIndex` + 矢印キー対応にする。
- メニューに矢印キー移動、Home/End、Esc 閉じる、開いた直後の先頭項目フォーカスを実装する。
- 共通の `Dialog` コンポーネントを作り、初期フォーカス・フォーカストラップ・Esc 閉じる・`aria-labelledby` を統一する。

## U-06 `Ctrl+F` で文書内検索とパッケージ検索が競合する

**重大度**: High / **区分**: キーボード操作

**対応状況（フェーズ2・実装済み）** — 文書内検索を `Ctrl/Cmd+F`、パッケージ検索を `Ctrl/Cmd+Shift+F` に分離し、処理済みイベントをグローバル側で除外する。

**確認結果** — Windows Tauri 版（`1f485cb`）で Vim をオフ・オンに切り替え、各状態で `Ctrl+F` は文書内検索だけ、`Ctrl+Shift+F` はパッケージ検索だけを開くことを確認した。Esc でパネルが閉じ、パッケージ検索を閉じた後は編集欄にフォーカスが戻った。WebView2 のアクセシビリティツリーではパッケージ検索の領域名と、フォーカス中の「検索語」入力欄を確認した。

**ナレーター追加確認（2026-11-07）** — `Ctrl+Shift+F` でパッケージ検索を開くと、Windows ナレーターの「スピーチの要約」に「パッケージを検索 セクション, 検索語, 編集, 検索」と記録された。検索の領域名、入力欄の名前と役割が読み上げられた。

**Cmd 相当の追加確認（2026-11-08）** — Windows の Firefox 159.0.1 で `navigator.platform` を `MacIntel` に設定し、編集欄に `metaKey` の合成キーイベントを送った。Vim のオン・オフの両方で `Meta+F` は文書内検索だけ、`Meta+Shift+F` はパッケージ検索だけを開いた。

**macOS CI の追加確認（2026-11-08）** — macOS 15.8.2 の WKWebView に AppKit のキーイベントを送り、Vim のオン・オフそれぞれで `Cmd+F` と `Cmd+Shift+F` が別々の検索を開くことを確認した。WKWebView は4イベントを `isTrusted` が真のイベントとして受け取った。物理 Mac のキーボードは未検証。[検証条件と結果](improvement-plan.md#macos-ci-での-u-06-と-u-32-の検証2026-11-08)

**macOS 配布版の確認（2026-11-08）** — macOS CI でリリース用 `.app` を起動し、Vim のオン・オフの両方で、2つの Cmd ショートカットが対応する検索だけを開くことを確認した。[配布版の検証](improvement-plan.md#macos-配布版のメニューの検証2026-11-08)

**根拠と検証**
- `CodeEditor.tsx:86-87` の CodeMirror `basicSetup` は文書内検索のキーバインドを含む。
- `App.tsx:1254-1265` のグローバルハンドラも `Ctrl/Cmd+F` を処理し、`event.defaultPrevented` を確認せずパッケージ検索を開く。
- jsdom で Vim 無効時に `Ctrl+F` を送ると、文書内検索パネルが開き、処理済みのイベントでパッケージ検索の起動処理も走った。

**ユーザーへの影響**
文書内を探す操作でパッケージ検索も起動し、フォーカスがパッケージ検索欄に移る。

**改善案**
- 文書内検索は `Ctrl/Cmd+F`、パッケージ検索は `Ctrl/Cmd+Shift+F` に分ける。処理済みイベントをグローバルハンドラで無視し、アプリ内に両方のキーを表示する（U-29）。

## U-07 Markdown の分割表示で、編集のたびに全件診断が走る

**重大度**: High / **区分**: 体感性能

**対応状況（フェーズ3・追補対応済み）** — ライブ診断は編集後300 ms待ち、編集中の Markdown と直接リンクする Markdown のリンクを検査する。手動診断は最新のパッケージ全体をすぐに検査する。

**確認結果** — 100件×5,248文字の合成データで、1件変更後の診断は改善前315.2〜395.4 ms、改善後7.0〜8.7 ms。Tauri/WebView2で20入力を測り、入力からプレビューの描画フレームまで30.0〜161.6 msだった。

**Windows 実機の改善前後比較（2026-11-08）** — 短い本文と表付きの長い本文を、1ファイルと100ファイルの4条件で比較した。各版・各条件で同じ1文字の入力と削除を40操作計測した。短い本文の100ファイル条件では描画までの中央値が 176.4 ms → 10.0 ms に短縮した。表付きの長い本文の100ファイル条件では 377.8 ms → 170.2 ms だった。[Windows 実機の計測条件と結果](improvement-plan.md#windows-での-u-07-入力性能の比較2026-11-08)

**表付き長文の描画改善と再計測（2026-11-08）** — 表解析の依存パッケージを2.1.2に更新し、編集後もプレビューの見出しと表を維持するようにした。Windows 実機では、表付き長文の入力から描画までの中央値が、1ファイルで 168.4 ms → 69.1 ms、100ファイルで 165.6 ms → 164.1 ms だった。100ファイルでは中央値の差が小さく、p95 は189.8 msから203.7 msに増えた。[追補の実機計測](improvement-plan.md#windows-での-u-07-表付き長文の描画改善2026-11-08) · [PR #34](https://github.com/mdpkg/MaCaEditor/pull/34)

**診断範囲と描画の再計測（2026-11-08）** — ライブ診断のリンク検査を編集中の Markdown と直接リンクする Markdown に絞り、手動診断はパッケージ全体を検査する。構文が変わらない長文の文字編集では解析結果を再利用する。Windows 実機で、表付き長文の中央値は1ファイルで 81.6 ms → 18.2 ms、100ファイルで 72.8 ms → 20.3 ms。100ファイル条件の p95 は 80.8 ms → 21.8 ms だった。[Windows 実機での再計測](improvement-plan.md#windows-での-u-07-診断範囲と描画の再計測2026-11-08) · [PR #41](https://github.com/mdpkg/MaCaEditor/pull/41)

**根拠**
- `App.tsx:1535` で `diagnosticRanges={diagnosePackage(doc)...}` を JSX 内で直接呼んでいる。
- `src/lib/packageDiagnostics.ts` の `diagnosePackage` は全ファイルを走査し、各 Markdown を `markdownLinks` で解析する。
- `handleContentChange` が本文の変更で `doc.files` を更新するため、分割表示の再レンダーで全件診断が走る。

**ユーザーへの影響**
リンクを含む各 5,248 文字の合成 Markdown 100 件を使った Node.js での計測では、診断関数単体がウォームアップ後の 5 回で 300〜351 ms かかった。Windows 実機での改善前後の計測結果は上記を参照。

**改善案**
- 変更のない Markdown のリンク解析結果を再利用する。`doc.files` を依存にした `useMemo` だけでは、入力ごとの全件診断が残る。
- 入力中の診断はデバウンスし、診断一覧を明示的に開くときは最新の文書を全件診断する。
- 診断対象を編集中ファイル＋リンク先に限定した軽量版を用意する。

## U-08 ファイル切替・Vim 切替でカーソル位置が失われる

**重大度**: Medium / **区分**: 編集継続性

**対応状況（フェーズ3・実装済み）** — ファイル別のカーソル位置とスクロール位置を保持し、Vim の切替はエディタを作り直さず適用する。

**確認結果** — 自動テストでファイル往復と Vim 切替時のエディタ・選択・履歴を確認。Windows 版でカーソル位置2000とスクロール位置420の復元を確認。

**根拠**
- `App.tsx` の分割表示で `<MarkdownEditor key={displayFile.path} ...>` と `key` をパスにしているため、ファイルを切り替えるたびに CodeMirror が再生成される。
- `src/components/CodeEditor.tsx:176` の effect 依存が `[language, vimMode]` で、Vim mode を切り替えると `EditorView` を作り直す。
- 直近のカーソル位置は `editorCursorRef` に記録するが、ファイル別の保持はない。再生成時の初期位置には検索などの遷移用の `navigationPosition` が渡る。

**ユーザーへの影響**
- ファイルを行き来すると、戻ったときに先頭付近へ戻る。長い文書では毎回スクロールし直す必要がある。
- Vim mode を切り替えるとカーソルが失われ、編集中の位置を見失う。

**改善案**
- ファイルごとのカーソル位置・スクロール位置を Map で保持し、切替時に復元する（プレビューのスクロール位置には既存の復元処理があるため、エディタ側の位置を別に保持する）。
- Vim mode 切替は `Compartment` で動的に再構成し、`EditorView` を作り直さない。

**改善案**

## U-16 画像ドロップで一部が非対応でも除外されたファイルが分からない

**重大度**: Medium / **区分**: フィードバック

**対応状況（フェーズ5・追補対応済み）** — 画像の成功、非対応による除外、読込失敗を件数とファイル名で通知し、成功分を取り込む。Windows では非対応形式だけの選択をネイティブドラッグ中に拒否する。

**確認結果** — 統合テストと Windows 版の Tauri イベント送信で、成功・除外・失敗が各1件の組み合わせを確認。Explorer から PNG 1件をマウスでドラッグし、画像がツリーに追加されることを確認した。保存後に画像の SHA-256 が取り込み元と一致し、Markdown に画像参照があることを確認した。[実機検証](improvement-plan.md#windows-の-explorer-からのドロップ検証2026-11-07)

**混在ドロップの確認結果** — Explorer で `mixed-supported.png` と `excluded-sample.txt` を同時に選択してドロップした。警告通知に取り込み1件と除外1件のファイル名が表示された。保存した `.mdpkg` を読み返し、元の PNG と SHA-256 が一致する画像と Markdown の参照があり、TXT は収録されていないことを確認した。[実機検証](improvement-plan.md#windows-の-explorer-からのドロップ検証2026-11-07)

**読込失敗を含む混在ドロップ（2026-11-08）** — Explorer から正常な PNG、非対応の TXT、別プロセスで排他ロックした PNG をまとめてマウスでドロップした。取り込み・除外・失敗が各1件とファイル名付きで通知された。保存した `.mdpkg` には正常な PNG と本文の画像参照だけが追加され、PNG の SHA-256 は取り込み元と一致した。[Windows 実機の検証記録](improvement-plan.md#windows-explorer-からの-u-16-混在ドロップ検証2026-11-08)

**ドロップ可否と保存の再検証（2026-11-08）** — Windows 実機の標準 OLE 経路で、非対応 TXT 単独への拒否、フォルダ・パッケージの読込、混在画像の通知と正常な PNG の保存を確認した。最終版では Explorer のマウス操作で禁止カーソルとパッケージが開くことも確認した。[Windows 実機での OLE 再検証](improvement-plan.md#windows-での-u-16-ドロップ可否と保存の再検証2026-11-08) · [PR #42](https://github.com/mdpkg/MaCaEditor/pull/42)

**根拠**
- `App.tsx` の `handleDropImages` は `isSupportedImageName` で絞り込み、0 件なら `setError("Drop PNG, JPEG, GIF, WebP, or BMP image files.")` を出す。
- 一部だけ非対応の場合、対応分だけ処理し、除外されたファイル名は通知しない。
- `imageImport.ts` の `droppedFileToImage` は非対応で例外を投げるが、呼び出し側は `Promise.all` 全体を catch して `String(e)` を表示する。

**ユーザーへの影響**
複数ファイルをまとめてドロップしたとき、どれが取り込まれ、どれが失敗したのか分からない。エラー文言も英語で、次に何をすればよいか不明。

**改善案**
- 取り込み結果を「成功 n 件 / 失敗 m 件（ファイル名）」で通知する。
- 非対応形式はドロップ時点でカーソルが「不可」になるよう `dropEffect = "none"` を返す。

## U-19 テーブル編集に全体キャンセルがなく、履歴が二重になる

**重大度**: Medium / **区分**: 編集

**対応状況（フェーズ3・実装済み）** — 完了まで表の変更を下書きに保持し、キャンセルで破棄する。確定時に元の本文が変更されていないことを確認する。

## U-21 保存待ちの間の編集が失われるおそれがあり、多重実行ガードもない

**重大度**: High / **区分**: データ保全・フィードバック

**対応状況（フェーズ1・実装済み）** — 保存・名前を付けて保存の完了後も後続の編集を未保存として保持する。保存・書き出し中は処理状態を表示し、多重実行を防ぐ。

**確認結果** — 保存応答を遅らせる統合テストで後続編集と多重保存防止を確認。2026-11-07 に Windows Tauri 版（`1f485cb`、WebView2）で再検証した。「保存」と「名前を付けて保存」は実際に `.mdpkg` へ書き込み、WebView に返す完了応答をそれぞれ1,484 ms・1,510 ms保留した。保留中は両メニュー項目が無効で、`Ctrl+S` を2回押しても保存コマンドは各ケース1回だった。応答後も追記と未保存表示が残り、次の `Ctrl+S` で追記が書き込まれることを実ファイルの読み戻しで確認した。名前を付けて保存した後の再保存先はコピーで、元のパッケージにはコピー側の追記が入らなかった。

**検証条件** — 一時パッケージを使用し、完了応答を検証用に保留した。名前を付けて保存する際は選択ダイアログの返却先を一時ファイルに固定した。

**根拠**
- `App.tsx:490-525` の `performSave` と `performSaveAs` は、開始時点の `doc` を使って非同期保存し、完了後にそのスナップショットを保存済みとして `setDoc` に渡す。`documentPersistence.ts:12` の `saveDocument` も引数の状態をもとに保存済み状態を返す。
- 保存中の表示や実行ガードがなく、Save メニューや `Ctrl/Cmd+S` から再度保存を要求できる。Folder モードのパッケージ書き出しにも処理中表示や多重実行ガードはない。

**ユーザーへの影響**
保存待ちの間に受理された編集が、完了時に古い内容で上書きされる可能性がある。書き出しは編集中の文書状態を置き換えない。編集消失はコード上のリスクで、Tauri 実機では未再現。

**改善案**
- 保存・書き出し中は進行状態を表示し、メニュー、ショートカットなどの入口で多重実行を防ぐ。
- 保存完了時に保存対象と最新の文書・編集状態を照合し、後続の編集を保持する。保存開始後に編集された内容は未保存として扱う。

## U-22 エラー表示が編集後も残り続ける

**重大度**: Medium / **区分**: 状態管理

**対応状況（フェーズ1・実装済み）** — 同じ操作が成功したときや文書を入れ替えたときにエラーをクリアする。無関係な編集では保存失敗の情報を維持する。

## U-23 ステータスバーが `Error` だけで原因が分からない

**重大度**: Medium / **区分**: フィードバック

**対応状況（フェーズ1・実装済み）** — ステータスバーに失敗した操作と短い原因を表示する。日本語の短い原因を用意できない場合は詳細欄へ案内する。

## U-31 本文の「目次」節がプレビューで置き換わる

**重大度**: Medium / **区分**: 表示

**対応状況（フェーズ1・実装済み）** — TOC の設定に応じて生成処理を切り替え、本文の「目次」と生成目次を区別した。

**確認結果** — プレビューの回帰テストと Windows 実機で、目次をオン・オフしても本文の「目次」節と次の節の段落が残ることを確認。実機では生成目次と節リンクはオンのときだけ表示された。[Windows 実機の検証記録](improvement-plan.md#windows-のフェーズ1追加検証2026-11-08)
